# Демо-набор: закешированные ответы стадий

При `DEMO_MODE=true` (значение по умолчанию) сервис читает ответы отсюда и **не обращается
к vision-API**. Ключ не нужен: проект запускается и проходит сценарий целиком у любого
проверяющего.

Имя файла — `<снимок>.<стадия>.json`, стадии две: `triage` и `extract`.

## Поле `origin` — читайте его первым

| Значение | Что это |
|---|---|
| `model` | **настоящий ответ модели**, сохранённый при живом вызове. Есть `usage` — замер токенов |
| `hand_marked` | размеченный вручную эталон этапа 1, положенный сюда как затравка |

Различие принципиальное. Затравка позволяет прогнать конвейер до того, как сделан хоть
один живой вызов, но **эталоном точности она быть не может**: мерить модель по эталону,
который написан не моделью, значит мерить не то. По мере живых прогонов файлы `hand_marked`
замещаются файлами `model`, и на этапе 5 точность считается только по вторым.

Сейчас все файлы — `hand_marked`: живых прогонов через `cli.py` ещё не было.

## Как набор пополняется сам

`extract_sign_data` и `classify_image` сохраняют сюда каждый успешный живой ответ вместе
с `usage`. Отдельной работы по сбору демо-набора не нужно — он собирается по ходу дела,
а не доделывается в конце.

Оттуда же берутся замеры для таблицы экономики отсева: `python cli.py economics`
читает `usage` из этих файлов.

## Почему демо не может «работать иначе»

Ветка демо-режима стоит **в источнике данных**, а не в логике: дальше по конвейеру
и живой ответ, и закешированный идут одним и тем же путём — та же валидация, тот же
справочник, тот же движок. Разойтись поведение может только в том, откуда взялся JSON.
